# PROJECT BLUEPRINT — «Азбука Музыки»

Этот документ описывает устройство приложения учёта для музыкального клуба
так, чтобы по нему можно было построить аналогичное приложение для другого
бизнеса (например, волейбольного клуба). Пароли, ключи и токены нигде не
приводятся — только названия переменных окружения.

---

## 1. Стек технологий

| Слой | Что используется |
|---|---|
| Язык | JavaScript (JSX) — вся бизнес-логика и UI в одном файле; TypeScript — только обвязка Next.js (`layout.tsx`, `page.tsx`, `supabase.ts`) |
| Фреймворк | **Next.js 16** (App Router), собирается в **статический экспорт** (`output: "export"` в `next.config.ts`) — то есть результат сборки это чистые HTML/JS/CSS файлы без серверной части Next.js |
| UI-библиотека | React 19, без сторонних UI-китов. Tailwind CSS подключён в `devDependencies`, но фактически **не используется** — все стили заданы инлайн, через JS-объекты (`style={{...}}`) |
| База данных | **Supabase** (управляемый PostgreSQL) — 6 таблиц + встроенная таблица пользователей `auth.users` |
| Как хранятся данные | Браузер обращается к Supabase напрямую через `@supabase/supabase-js` (REST поверх Postgres, он же PostgREST). Отдельного бэкенд-сервера нет — доступ к данным регулируется через **Row Level Security (RLS)** политики в самой базе, а не через код приложения |
| Хостинг и деплой | **Netlify**. Статический сайт деплоится из GitHub-репозитория: пуш/мерж в ветку `main` → автосборка на Netlify. Один-единственный кусочек серверного кода — **Netlify Function** (`netlify/functions/create-teacher.js`), которая использует привилегированный ключ Supabase (`SUPABASE_SERVICE_ROLE_KEY`) для создания новых учётных записей педагогов. Это единственное место, где секретный ключ используется — он никогда не попадает в браузер |
| Авторизация пользователей | **Supabase Auth** (email + пароль). Роли — НЕ встроенная фича Supabase, а своя колонка `role` в таблице `teachers` (`admin` / `teacher`), привязанная к пользователю Supabase Auth через `auth_user_id` |
| PWA / мобильная установка | `public/manifest.json` + иконки — приложение можно «установить» на главный экран телефона как отдельное приложение (Android/Chrome — полноценно, iOS/Safari — иконка на столе) |

### Переменные окружения
- `NEXT_PUBLIC_SUPABASE_URL` — публичный URL проекта Supabase (встраивается в сборку)
- `NEXT_PUBLIC_SUPABASE_ANON_KEY` — публичный (anon/publishable) ключ Supabase, тоже встраивается в сборку, безопасен для браузера
- `SUPABASE_SERVICE_ROLE_KEY` — **секретный** ключ, используется только внутри Netlify Function, никогда не должен попасть в клиентский код (переменная без префикса `NEXT_PUBLIC_` специально, чтобы Next.js не встроил её в бандл)

**Важная особенность архитектуры**: почти весь код сознательно лежит в одном файле

Это не «правильная» модульная структура, а осознанный компромисс ради простоты
правок в рамках одного проекта. Для нового проекта такого масштаба это
приемлемо, но при росте стоит разнести на отдельные файлы (`screens/`,
`modals/`, `lib/api.js` и т.д.).

## 3. Схема данных (Supabase / Postgres)

Все таблицы в схеме `public`, RLS включён на всех. Два уровня доступа:
- `authenticated_all_*` — любой залогиненный пользователь (admin или teacher) может читать/писать
- `admin_all_*` — только пользователь с `teachers.role = 'admin'` (проверка через подзапрос к `teachers` по `auth.uid()`)

### `teachers` (педагоги/сотрудники)
| Поле | Тип | Назначение |
|---|---|---|
| `id` | integer, PK | |
| `name` | text | Имя |
| `email` | text, unique | Email — он же логин в Supabase Auth |
| `role` | text, CHECK (`admin`/`teacher`) | Роль для прав доступа |
| `directions` | text[] | Направления, которые ведёт педагог (аналог специализации) |
| `auth_user_id` | uuid, unique, FK → `auth.users(id)` ON DELETE CASCADE | Связь с учётной записью Supabase Auth |
| `created_at` | timestamptz | |

Доступ: `authenticated_all_teachers` (читают/пишут все залогиненные).

### `students` (клиенты/ученики)
| Поле | Тип |
|---|---|
| `id` | integer, PK |
| `full_name` | text, NOT NULL |
| `birth_date` | date |
| `is_minor` | boolean |
| `parent_name`, `parent_phone` | text (для несовершеннолетних) |
| `phone` | text, NOT NULL |
| `messenger` | text (Telegram / VK·Макс / SMS — просто справочное поле, без интеграции) |
| `messenger_contact` | text |
| `directions` | text[] |
| `created_at` | timestamptz |

Доступ: `authenticated_all_students`.

### `subscriptions` (абонементы)
| Поле | Тип |
|---|---|
| `id` | integer, PK |
| `student_id` | integer, FK → `students(id)` |
| `direction` | text, NOT NULL |
| `type_key` | text (ключ тарифа, см. §5) |
| `type_label` | text (человекочитаемое название) |
| `price` | integer |
| `total_lessons` | integer |
| `lessons_left` | integer |
| `purchase_date`, `expiry_date` | timestamptz |
| `status` | text (`active` / `expired`) |
| `payment_method` | text (просто текст: «Наличные» / «Перевод», без интеграции с платёжкой) |
| `created_at` | timestamptz |

Доступ: `authenticated_all_subscriptions`.

### `schedule` (занятия/расписание)
| Поле | Тип |
|---|---|
| `id` | integer, PK |
| `student_id` | FK → `students` |
| `teacher_id` | FK → `teachers` |
| `sub_id` | FK → `subscriptions` (nullable — занятие может быть без привязки к абонементу) |
| `direction` | text, NOT NULL |
| `date` | timestamptz, NOT NULL (дата+время занятия) |
| `status` | text (`planned` / `attended` / `missed` / `rescheduled`) |
| `access_link` | text (ссылка-пропуск в помещение, отправляется вручную) |
| `created_at` | timestamptz |

Доступ: `authenticated_all_schedule`.

### `expenses` (расходы) — **видно только админу**
| Поле | Тип |
|---|---|
| `id` | integer, PK |
| `category` | text (Аренда/Налоги/Уборка/Реклама/Оборудование/Прочее) |
| `amount` | integer |
| `date` | timestamptz |
| `comment` | text |
| `created_at` | timestamptz |

Доступ: `admin_all_expenses` — педагоги эту таблицу не видят вообще (RLS фильтрует на уровне строк).

### `income` (прочие доходы, напр. аренда помещения) — **видно только админу**
Структура идентична `expenses`, только суммы идут в плюс, а не в минус.
Категории по умолчанию: «Аренда 400₽/ч», «Аренда 500₽/ч», «Другое».

Доступ: `admin_all_income`.

### `auth.users` (управляется Supabase)
Email/пароль, стандартная таблица Supabase Auth. Связь с бизнес-данными —
только через `teachers.auth_user_id`.

### Связи (ER, упрощённо)
```
auth.users 1───1 teachers
teachers   1───N schedule (teacher_id)
students   1───N subscriptions (student_id)
students   1───N schedule (student_id)
subscriptions 1───N schedule (sub_id, может быть NULL)
```
`expenses` и `income` — независимые таблицы, ни на что не ссылаются.

## 4. Экраны и функции

Нижняя навигация (5 вкладок, «Финансы» скрыта для роли `teacher`):

1. **Сегодня** — три карточки-счётчика (учеников всего / занятий в этом месяце /
   доход за месяц), список сегодняшних занятий. По клику на занятие —
   быстрые действия: «Пришёл», «Пропуск», «Перенос», «Отправить пропуск»
   (генерирует текст сообщения для отправки вручную в мессенджер),
   «Изменить», «Удалить».
2. **Ученики** — поиск по имени/телефону, список с цветным бейджем статуса
   абонемента, кнопка «Добавить ученика». Клик открывает карточку ученика.
   - **Карточка ученика** — 3 вкладки: *Абонементы* (активные + история,
     кнопка «Новый абонемент», отметка посещения), *Журнал* (вся история
     занятий), *Карточка* (контакты, кнопки «Редактировать» / «Удалить
     ученика»).
3. **Расписание** — недельный календарь (листается стрелками), выбор дня,
   список занятий на день, кнопка «Добавить занятие» (с автоматическим
   подбором активного абонемента по ученику+направлению).
4. **Финансы** *(только для роли admin)* — листание по месяцам (стрелки),
   4 карточки (Доход / Расходы / Зарплата / Прибыль), блок расчёта зарплаты
   педагогам, список поступлений от абонементов, список «прочих доходов»
   (аренда и т.п.) с возможностью добавить/удалить, список расходов с
   возможностью добавить/удалить.
5. **Педагоги** — список педагогов с ролью и направлениями. Для админа —
   кнопка «Добавить педагога» (email + роль + направления → создаёт
   настоящую учётную запись через Netlify Function, показывает одноразовый
   временный пароль для передачи педагогу), «Редактировать», «Удалить».

Общие элементы:
- **Шапка**: логотип, кнопка «Пароль» (смена своего пароля без похода в
  админку Supabase), кнопка «Выйти».
- **Экран входа**: email + пароль, ссылка «Забыли пароль?» → отправка письма
  со ссылкой восстановления → отдельный экран установки нового пароля.

## 5. Бизнес-логика расчётов

### Абонементы
Фиксированный каталог тарифов (`SUB_TYPES`) — ключ, название, кол-во занятий,
цена. При покупке создаётся запись `status: "active"`, `lessons_left = total_lessons`.
При отметке занятия «Пришёл»/«Пропуск» `lessons_left` уменьшается на 1.
**Важно**: когда `lessons_left` доходит до 0, абонемент автоматически
переводится в `status: "expired"` — без этого старый исчерпанный абонемент
оставался бы «активным» навсегда и мешал подхватить новый.

### Подбор абонемента при планировании занятия
Ищется первый абонемент ученика с тем же направлением, `status==="active"`
**и** `lessons_left > 0`. Если несколько «активных» (не должно случаться
после фикса выше, но на всякий случай) — защита всё равно есть.

### Зарплата педагогов
- `TEACHER_RATE = 800₽` — ставка за обычное занятие
- `TRIAL_TEACHER_RATE = 500₽` — ставка за занятие по пробному абонементу (дешевле)
- Считается по **всем** занятиям месяца со статусом `attended`, без деления
  по конкретному педагогу — единая ставка для всех (сознательное решение
  владелицы бизнеса, а не технологическое ограничение).
- `Зарплата = (обычных занятий × 800) + (пробных занятий × 500)`

### Доход / Расходы / Прибыль (на вкладке Финансы, за выбранный месяц)
- `Доход = сумма цен купленных в этом месяце абонементов + сумма "прочих доходов"`
- `Расходы = сумма ручных расходов + начисленная зарплата`
- `Прибыль = Доход − Расходы`

### Индикаторы на карточках ученика
- `subAlert()` — цвет бейджа абонемента: danger (≤1 занятия), warning (2
  занятия), иначе нет подсветки.
- `subDateExpired()` — абонемент просрочен по дате, но занятия ещё остались.

Эти индикаторы — **только** визуальные бейджи в списках/карточках.
Проактивные баннеры-уведомления («абонемент скоро закончится» и т.п.) были
сознательно убраны с главного экрана — владелица сочла их визуальным шумом,
раз нет настоящей рассылки клиентам.

### «Долгов» как отдельного понятия нет
Нет расчёта «ученик должен N рублей» — финансовый учёт идёт только по факту
покупки абонемента (оплата считается состоявшейся в момент покупки).

## 6. Отчёты и экспорт

**Отсутствуют полностью.** Нет экспорта в Excel/CSV, нет PDF-отчётов, нет
графиков/диаграмм. Все цифры — просто текстовые карточки внутри интерфейса,
без возможности выгрузить или напечатать. Это осознанный пробел — при
повторении архитектуры для другого бизнеса стоит заложить это сразу, если
отчётность важна.

## 7. Подключённые сервисы и интеграции

Кроме самих Supabase и Netlify — **ничего**:
- Нет Telegram-бота и push-уведомлений.
- Нет интеграции с платёжными системами — способ оплаты это просто текстовое
  поле («Наличные» / «Перевод»), без реального платёжного шлюза.
- «Мессенджер» ученика — справочное текстовое поле; кнопка «Отправить
  пропуск» лишь формирует текст сообщения, отправка — вручную, копированием.
- Email отправляется только Supabase Auth (для входа/сброса пароля), через
  встроенный почтовый сервис Supabase, у которого **жёсткий лимит писем**
  (рассчитан на разработку, не на продакшен) — см. §9.

## 8. Дизайн

- **Цвета** — единый объект `T` в начале файла:
  - фон `#F8F6F3`, основной текст/кнопки `#1A1A1A` (чёрный), акцент
    (терракотовый) `#C94A2A`, плюс пары цвет/подложка для success (зелёный),
    warning (жёлтый/коричневый), danger (красный), всё приглушённое,
    не кричащее.
  - Отдельная палитра `TC` — 4 цвета для визуального различения педагогов
    в расписании (по остатку от деления id).
- **Шрифт** — системный стек: `-apple-system, BlinkMacSystemFont, 'Segoe UI', Roboto, sans-serif` (без подключения внешних шрифтов).
- **Компоненты** — скруглённые карточки (`borderRadius: 12–16px`), лёгкие тени,
  крупные читаемые кнопки, инлайн-SVG иконки (без иконочных библиотек).
- **Адаптация под телефон**:
  - Весь интерфейс рассчитан на один столбец, `maxWidth: 480px`,
    центрированный — одинаково хорошо смотрится и на телефоне, и в узком
    окне десктопа.
  - Корневой контейнер — `height: 100dvh` + `display:flex; flexDirection:column`:
    шапка и контент скроллятся во внутренней области, а нижняя панель вкладок
    — обычный flex-элемент (НЕ `position:fixed`). Это принципиально: на
    iOS Safari `position:fixed` при скролле «прыгает» вместе с анимацией
    адресной строки — через flex-колонку эта проблема устранена полностью.
  - PWA: `manifest.json` + иконки → установка на домашний экран как
    отдельное приложение, без адресной строки браузера.

## 9. Что было сложным / что ломалось

Это реальные баги, найденные и исправленные в процессе эксплуатации —
полезный чек-лист для похожего проекта:

1. **Порядок удаления при каскаде.** Удаление ученика сначала удаляло саму
   запись, а потом — связанные абонементы/занятия. База отклоняла это
   (нарушение внешнего ключа), и удаление ученика попросту не работало.
   Исправлено — сначала удаляются дочерние записи, потом родительская.
2. **Зашитый ID вместо реального.** На старте разработки часть кода
   ссылалась на `teacherId: 1` как на «владельца по умолчанию» (осталось от
   демо-данных). Когда реальные ID педагогов в базе оказались другими,
   запись в расписание падала с ошибкой внешнего ключа — выглядело как
   «абонемент не принимается». Исправлено — используется ID реального
   залогиненного педагога / первого в списке.
3. **Часовой пояс в датах.** Функция построения строки «дата» использовала
   `.toISOString()`, которая переводит время в UTC. Для часового пояса
   впереди UTC (Москва, UTC+3) это иногда сдвигало дату на день назад —
   в календаре было видно одно число, а в заголовке над списком занятий
   другое. Исправлено — дата строится из локальных компонентов
   (`getFullYear/getMonth/getDate`), без прохода через UTC.
4. **Абонемент «залипал» активным.** После того как у абонемента
   заканчивались занятия, его статус не менялся — он навсегда оставался
   `active`. При покупке нового абонемента на то же направление в базе
   оказывалось два «активных» абонемента, и приложение продолжало находить
   старый (пустой). Исправлено — абонемент автоматически помечается
   `expired` в момент, когда заканчиваются занятия.
5. **Рассинхрон CHECK-ограничения в базе и кода.** Когда роли упростили с
   3 (`admin/active/passive`) до 2 (`admin/teacher`), соответствующее
   ограничение `CHECK` в самой таблице Postgres не обновили — добавление
   нового педагога стабильно падало с ошибкой `teachers_role_check`.
   Это показывает: при изменении допустимых значений в коде нужно помнить
   и про constraints в БД, это две разные вещи.
6. **Лимит на email у Supabase.** Встроенная отправка писем Supabase Auth
   жёстко лимитирована (рассчитана на тестирование, не на продакшен) —
   восстановление пароля быстро упёрлось в «email rate limit exceeded».
   Для реальной эксплуатации нужен свой SMTP (Authentication → Emails →
   SMTP Settings в Supabase).
7. **Потеря собственной админской записи.** Во время тестирования владелица
   случайно удалила свою же запись в `teachers` (кнопкой «Удалить» в списке
   педагогов) — учётная запись Supabase Auth осталась, но привязка к роли
   пропала, вход стал невозможен («Аккаунт не привязан к профилю
   преподавателя»). Восстановили через SQL-запрос напрямую в Supabase.
8. **`position: fixed` на iOS.** См. §8 — нижняя панель вкладок «прыгала»
   при скролле на iPhone, решено переходом на flex-колонку без
   `position:fixed`.
9. **Среда разработки не персистентна.** `node_modules` и `.env.local`
   периодически пропадали между сессиями работы (особенность песочницы
   разработки) — приходилось переустанавливать зависимости и пересоздавать
   `.env.local` перед каждой сборкой.

## 10. Как запустить локально и обновить на сервере

### Локальный запуск
```bash
npm install
# создать .env.local в корне проекта:
#   NEXT_PUBLIC_SUPABASE_URL=...
#   NEXT_PUBLIC_SUPABASE_ANON_KEY=...
npm run dev       # разработка, http://localhost:3000
npm run build     # продакшен-сборка → папка out/ (статика)
```

### Деплой (уже настроено для этого проекта)
1. Код живёт в GitHub-репозитории, Netlify подключён к нему напрямую
   (continuous deployment).
2. Любой мерж в ветку `main` автоматически запускает сборку на Netlify
   (`netlify.toml`: `command = "npm run build"`, `publish = "out"`,
   `functions directory = "netlify/functions"`).
3. Три переменные окружения настраиваются в Netlify (Site configuration →
   Environment variables): `NEXT_PUBLIC_SUPABASE_URL`,
   `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY` (последняя —
   с пометкой «Contains secret values», доступна только сборке и функциям,
   не браузеру).

### Обновление схемы базы данных
**Важный пробел**: миграции базы данных **не версионируются в репозитории**
и не выполняются автоматически — каждое изменение схемы (новая таблица,
колонка, RLS-политика) выполнялось вручную через Supabase SQL Editor по
мере необходимости. Для нового проекта стоит с самого начала держать все
`.sql` миграции в репозитории (папка `supabase/migrations/` — родной формат
Supabase CLI) — это сильно упростит повторение и откат изменений.

## Итог: что взять как есть, а что переделать под волейбольный клуб

### Можно взять почти без изменений
- **Вся архитектура**: Next.js статический экспорт + Supabase + Netlify +
  Netlify Function для привилегированных операций — рабочая, недорогая,
  бесплатная на старте схема.
- **Авторизация и роли** (admin/teacher → для клуба, например,
  admin/тренер): экран входа, восстановление пароля, создание аккаунтов
  сотрудников через серверную функцию с одноразовым паролем.
- **Учёт расходов/доходов на Финансах** (включая «прочие доходы» — идеально
  подходит и для аренды зала/площадки в волейбольном клубе) + листание по
  месяцам.
- **Мобильная оболочка**: 100dvh flex-layout, нижняя навигация, PWA-установка
  на экран телефона — всё переносится один в один.
- **Паттерн CRUD через Supabase RLS** — без переписывания бэкенда, разве что
  с новыми именами таблиц.
- **Цветовая тема/дизайн-система** — как стартовая точка, легко перекрасить
  под другой бренд, меняя один объект `T`.

### Нужно переделать под специфику волейбольного клуба
- **Модель занятия "1 ученик : 1 педагог" → групповые тренировки.**
  Сейчас `schedule` — это запись «один ученик, один педагог, одно время».
  Для волейбола тренировка обычно групповая (команда/группа одновременно),
  поэтому нужна другая модель: `training_sessions` (дата, время, тренер,
  команда/группа) + отдельная таблица посещаемости `attendance`
  (many-to-many: сессия × ученик × статус), а не абонемент-привязанная
  запись на человека.
- **Абонементы → членство/групповые тарифы.** Вместо «N занятий по
  направлению» вероятно понадобится «месячный абонемент на группу/команду»
  или «безлимит на месяц» — модель `subscriptions` стоит обобщить (не
  привязывать жёстко к штучным занятиям, если тариф — помесячный).
- **"Направления" → команды/возрастные группы.** `DIRECTIONS` (Вокал,
  Фортепиано...) напрямую заменяются на что-то вроде «Юноши 14-16»,
  «Взрослая лига», «Начинающие» и т.п. — механизм тот же (просто список +
  поле у ученика/тренера), менять нужно только сами значения.
- **Зарплата тренеров.** Сейчас это плоская ставка «за занятие». Для клуба,
  скорее всего, нужна ставка «за тренировку с группой» (не зависит от числа
  пришедших) — логика расчёта должна считать не по ученикам, а по сессиям.
- **Отчёты/экспорт.** Если клубу нужна отчётность для бухгалтерии или
  тренерского состава — этого нет вообще, нужно добавлять с нуля (например,
  экспорт посещаемости в Excel).
- **Реальные интеграции**, если понадобятся (SMS/Telegram-напоминания о
  тренировке, оплата онлайн) — в этом проекте их принципиально нет, их
  тоже предстоит строить с нуля поверх той же архитектуры.
